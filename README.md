# PodTube PWA — YouTube クライアント(ブラウザ / ホーム画面で動く版)

[mizuki20070314/podtube-ios12](https://github.com/mizuki20070314/podtube-ios12)(iOS 12 向けの非公式 YouTube クライアント、MIT)の機能を、
**PWA(ブラウザで動くアプリ)+ Python CGI** として作り直したものです。iPhone / iPad / Android / PC のどれでも、ホーム画面に追加して使えます。
画面・操作・機能は原作に合わせています(下の対応表)。

> 非公式です。YouTube / Google とは無関係です。内部 API を使うため、YouTube 側の変更で突然動かなくなることがあります。

- 公開先: <https://my-dev.sakura.ne.jp/podtube/>(さくらのレンタルサーバ、`~/www/podtube/`)
- アクセスキー: サーバーの `~/.podtube/config.json` の `access_key`。**初回だけ** `https://my-dev.sakura.ne.jp/podtube/#key=<キー>` を開くと、端末に覚えます(アドレスの `#key=…` はすぐ消えます)。
- ホーム画面に追加: iPhone / iPad は Safari の共有 → 「ホーム画面に追加」、Android の Chrome は「アプリをインストール」、PC の Chrome / Edge はアドレスバーのインストールボタン。

## 仕組み

```
ブラウザ(PWA: 素の JavaScript, ES2018)
   │  https://my-dev.sakura.ne.jp/podtube/            静的ファイル(index.html, assets/app.<hash>.js, sw.js …)
   │  https://my-dev.sakura.ne.jp/podtube/api.cgi/…   Python CGI(1 リクエスト = 1 プロセス、常駐しない)
   ▼
api.cgi ──→ YouTube InnerTube API(VISIONOS クライアント、ログイン時は TVHTML5 + OAuth 機器コード)
        └─→ googlevideo.com の HLS(マニフェストと映像・音声の断片を中継)
```

- **なぜ HLS を中継するのか**: 再生 URL は取得した側の IP に結び付いていて、googlevideo は CORS ヘッダを返しません。
  ブラウザが直接取りに行くと再生できないので、CGI がマニフェストを書き換えて(H.264 + AAC だけ、画質の上限、音声は 1 本だけ選ぶ、字幕は外す)、
  断片をそのまま流します。再生の識別は推測できないセッション ID だけです(`<video>` はヘッダを付けられないため)。
- **アクセスキー**: 鍵が無いと、サーバーが YouTube の中継として誰にでも使われてしまうので、既定で必須です(`require_key`)。
  鍵は `X-PT-Key` ヘッダか、`ptk` クッキー(HttpOnly / Secure / `Path=/podtube/`)で送られます。
- **データの置き場所**: 履歴・登録チャンネル・後で見る・高評価・再生リスト・設定・Google のトークンは**ブラウザの中だけ**(`localStorage`、キーは `pt.` で始まる)。
  サーバーに残るのは、再生中のセッション(8 時間で消える。`~/.podtube/cache/`)と、問題が起きたときの数行のログ(`~/.podtube/log/`)だけです。
  **サイトのデータを消すと、これらも消えます。**
- **ダウンロード**: 選んだ画質の HLS(マニフェストと断片)を Cache Storage(`pt-offline`)に保存し、Service Worker が Range 対応で返します。
- **Safari 12(iOS 12)で動く書き方**: 構文は ES2018 まで(`tests/check_syntax.js` で全ファイルを検査)、`gap`(flex)は `build/cssfix.py` が margin に直し、
  `position: sticky` には `-webkit-` を付けます。Apple の端末はネイティブ HLS、それ以外は hls.js(1.5.20)で再生します。

| ログイン(Google の機器コード、QR コード)と、アカウントのおすすめ / 登録チャンネル / 履歴 / 後で見る / 高評価 / 再生リスト、各操作の反映と巻き戻し、視聴履歴への記録(Samsung TV の身元) | 同じ |

PWA 版で足したもの: アクセスキー(と `#key=` のリンク)、共有ターゲット(`?url=` で開く)、Service Worker による起動の高速化とオフライン再生の配信。

ブックマークレット(原作の `podtube://` の代わり。YouTube のページを PodTube で開く):

```
javascript:location.href='https://my-dev.sakura.ne.jp/podtube/?url='+encodeURIComponent(location.href)
```

## できないこと・原作との違い

- バックグラウンドでのダウンロードの継続(PWA にはその仕組みが無い)。ダウンロード中は画面を開いておいてください。
- ブラウザが許さない機能は出しません(PiP のボタン、AirPlay のボタン、ロック画面の操作など)。iOS のホーム画面のアプリは、画面を閉じると音声が止まることがあります(OS の仕様。実機では未確認)。
- **ログイン中の履歴の並び**: アカウントの履歴には時刻がなく、新しい順に並んでいるだけです。原作は、このアプリで再生した動画のうちアカウントの最初の 1 ページに載っていないものを、すべて先頭に足していました。そのため、**「ショート」の棚の中にあるショート**(棚の中の動画を「載っている」と数えていませんでした)や、**1 ページ目より古い再生**が、本来の位置を無視して先頭に出ていました。PWA 版は、アカウントと端末の**両方に載っている動画を目印**にして、目印の間にあるアカウント側の項目に時刻を割り当て(位置に比例)、アカウントに無い再生をその時刻に当たる位置へ入れます。ページを読み込むたびに、それまでの全ページを基準に入れ直すので、古い再生は一覧がその時刻まで届いたときに現れます(アカウントに最後まで無ければ末尾)。目印が 1 つも無いときは、直近 2 時間の再生だけを先頭に出します。割り当ては推定なので、目印の間では数件ずれることがあります。You タブの棚も同じ規則です。
- **iOS の全画面**: iPhone / iPod touch の Safari には、ウェブページの一部を全画面にする機能がありません(Android・PC・iPad の Safari にはあります)。ページ内の要素の全画面は `requestFullscreen` ですが、iPhone では `<video>` そのものを OS 標準の動画プレーヤーで開く `webkitEnterFullscreen()` が、画面全体を使える唯一の方法です。そこで、**iPhone と、ホーム画面から開いた iPad は、全画面ボタンで OS 標準のプレーヤー(本当の全画面)を開きます**。代わりに、操作はこのアプリのものではなく iOS 標準になり(ダブルタップの ±10 秒、フィルムストリップ、チャプター表示などは使えません)、字幕は iOS の字幕メニューに出ます(アプリで字幕をオンにしていれば、字幕トラックを渡します)。設定の「全画面表示」(iOS だけに出ます)を「アプリ内」にすると、従来どおり、このアプリの操作パネルのまま、ブラウザの枠いっぱいに広げます(ブラウザの上下の帯は残ります)。iPad の Safari は、これまでどおりページごとの全画面です。iPhone を横向きにすると画面は全画面の配置になりますが、これは本当の全画面ではないので、全画面ボタンを押すと OS 標準のプレーヤーに切り替わります。
- **iOS のホーム画面アプリでは PiP が使えません**: iOS が、ホーム画面から開いたウェブアプリでの PiP を許可していません(WebKit の未修正の不具合 [303885](https://bugs.webkit.org/show_bug.cgi?id=303885)、[280627](https://bugs.webkit.org/show_bug.cgi?id=280627)。Apple も内部で追跡中。2026 年 7 月の報告では iOS 26.6 でも同じで、バグ票に回避策は載っていません)。このとき iOS は `document.pictureInPictureEnabled` を「可」と答えながら、実行を `NotSupportedError` で断ります。アプリは `video.webkitSupportsPresentationMode('picture-in-picture')` で見分けて、PiP のボタンを薄くし、押すと理由を表示します。**Safari で開くと PiP は使えます**(接続診断に、ブラウザの答えが出ます)。
- 原作が「できないこと」としている項目(コメントの投稿、ライブチャット、低評価数の表示、ショートの履歴記録など)は、同じく未対応です。
- 音声の選択は、サーバーが HLS から 1 本だけ残して返すため、切り替えるとその位置からマニフェストを読み直します(再生位置は保ちます)。

## 運用

サーバー側の設定は `~/.podtube/config.json`(最初の配備で一度だけ作られ、更新では上書きされません)。

| 項目 | 既定 | 意味 |
|---|---|---|
| `require_key` | `true` | `false` にすると、鍵なしで誰でも使えます(おすすめしません) |
| `access_key` | 配備時に乱数 | 変えると、全端末で入れ直しになります |
| `clients_url` | 原作の `config/clients.json` | クライアントのバージョンの上書き(1 時間キャッシュ)。壊れたときは原作と同じく、ここを書き換えれば直せます |
| `session_ttl` | 28800 | 中継セッションの寿命(秒) |

- **更新**: `python build/deploy.py`(ビルド → アップロード → 入れ替え → 公開 URL の確認。`--stage-only` で手元に書き出すだけ)。
- **止める / 消す**: `~/www/podtube` を消す(または名前を変える)だけです。常駐するものも cron もありません。
- **壊れたとき**: 設定 → 接続診断で、訪問者 ID / ホーム / プレーヤー / HLS のどこで失敗しているかが分かります。
- **「YouTube が一時的に再生を制限しています」**: サーバーの IP を YouTube が bot と見なし、再生用の問い合わせに「ログインして bot ではないことを確認してください」(`LOGIN_REQUIRED`)と答えている状態です(サーバーは HTTP 429 の `botcheck` で返します)。アプリのコードや動画のせいではありません。2026-11-07 に、さくらの共用 IP で実際に起きました(約 09:30 以降。同じ要求を自宅の回線から送ると、同じ動画が 3 種のクライアントとも通りました)。見分け方: `tests/diag_clients.py <サーバーの ~/.podtube> <動画 ID>` を**サーバーで**流し、手元の PC でも流して比べます(サーバーだけ `LOGIN_REQUIRED` なら IP の判定)。`tests/diag_timeline.py` は、サーバーで再生の解決が成功した時刻を一覧します(いつから止まったか)。待てば解けることがありますが、解ける保証はありません。
- **共用ホストの制約**: さくらは「アカウント全体の仮想メモリ約 2GB」を超えると最大のプロセスを止めます。CGI 1 つは約 31MB で、再生中は同時に 1〜3 本です。
  Immich など他のものと合わせた余裕を見てください。また、動画を中継するので転送量が増えます。YouTube の規約・さくらの規約の範囲で、自分用に使ってください。
  サーバーの IP が YouTube に制限されたときは、再生できなくなります(そのときは接続診断に出ます)。

## 開発とテスト

```
python tests/devserver.py 8080                 # 手元の疑似サーバー(静的ファイル + 本物の api.cgi)。PT_KEY=… で鍵を有効に
python tests/api_check.py <api.cgi の URL> [鍵]  # サーバーの通し検査 27 項目(本物の YouTube に当てる。手元でも本番でも可)
python tests/live_parse.py                     # パーサーを実際の応答に当てる
PT_KEY=<鍵> python tests/live_gate.py [URL]    # 鍵を持たない新規の訪問者として、鍵の画面・間違い・正しい鍵・#key= のリンクを確かめる(まっさらなヘッドレス Edge)
node tests/check_syntax.js <acorn.js>          # 全ファイルが ES2018 で読めるか(Safari 12)
python tests/smoke.py / t_*.py                 # ヘッドレス Edge(DevTools Protocol)で画面を操作して確かめる
python tests/t_ios.py [URL]                    # iOS の全画面ボタンと PiP の振り分け(WebKit だけの API を模擬して 47 項目)
python tests/t_sheet.py [URL]                  # 下から出るシート(チャプター 60 件など)が指でスクロールでき、引き下げて閉じられること(16 項目)
python tests/t_history.py [URL]                # ログイン中の履歴に端末の再生を時刻に合わせて入れる(作った例と偽のアカウント応答で 29 項目)
python build/build_web.py                      # build/out/web に書き出す
```

- `srv/podtube/` サーバーのコード(`innertube.py` クライアント、`parsers.py` 応答の解析、`yt.py` 呼び出し、`account.py` ログイン、`hls.py` 中継、`api.py` ルート)。Python 3.8 で動きます。
- `web/` 画面(`js/` は番号順に結合、`css/app.css`、`sw.js`、`vendor/`)。`js/01-icons.js` と `js/02-i18n.js` は原作の Swift から `build/gen_icons.py` / `build/gen_i18n.py` が生成します。
- 原作のソースは `../src-orig/`(読み取り専用の参照用)。

## 動作確認の状況

確認した:

- サーバーの通し検査 27 項目が、手元と**本番(さくら)の両方**で全て通る(ホーム、続き、検索、候補、動画、コメント、チャンネル、再生リスト、ショート、再生セッション、マスターの書き換え、断片、字幕、音声の選択、鍵の拒否)。
- 手元のヘッドレス Edge(スマホ・iPad・PC の幅、タッチ操作の模擬)で、ホーム / 検索 / 再生 / コメント / 全画面 / ショート / ダウンロード(保存・オフライン再生・削除)/ マイページ / 設定 / ログイン画面を、実際の YouTube のデータで操作。
- 本番の URL を実際の Chrome で: 鍵のリンクで開く、ホーム、動画の再生(1080p、画質を 360p に変えて解像度が変わること)、設定のシート、検索と候補、ショート、Service Worker が事前保存を終えること、gzip(JS 336KB → 89KB)。
- 本番の鍵の画面を、まっさらなブラウザ(新規の訪問者)で 7 項目(鍵の画面が出る、間違いは断られる、正しい鍵でホームが開く、再読み込みで覚えている、`#key=` のリンクで開いて鍵がアドレスから消える)。
- サーバーの IP から、Google のログイン用の機器コードを取得できること。

**まだ確認していない**(実機・実アカウントが要るもの):

- 実機の iOS(特に iOS 12)の Safari: ネイティブ HLS での再生、ホーム画面のアプリでの音声、ロック画面の操作、PiP、AirPlay。
- **iOS の OS 標準プレーヤーでの全画面と、PiP の見分け**: `webkitEnterFullscreen()` を使うのは、Apple の仕様どおりの呼び方(タップの中で、動画が読み込まれてから)ですが、確かめたのはヘッドレス Edge に WebKit の API の模擬を入れた試験(`tests/t_ios.py`)までで、実機の iPhone ではまだです。字幕のトラックが OS のプレーヤーに出るか、終了後に再生が続くか、画面の配置が戻るかは、実機で見る必要があります。
- Google アカウントでのログインの通し(コードの承認 → 画面が切り替わる)と、アカウントへの反映(視聴履歴への記録、高評価、登録、再生リスト)。コードの読み合わせまでです。原作も同じ理由で、反映の確認は「何も変えない」呼び出しだけでした。
- 実機の指でのスクラブ(押さえたまま横・上へ)。ヘッドレス Edge のタッチの模擬では動きます。
